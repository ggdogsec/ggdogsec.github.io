👔面试官：SSRF 了解吗？DNS 重绑定呢？

🙋‍♂️我：就是域名第一次解析成公网 IP，过了校验，第二次再解析成内网 IP，请求就打进去了。

👔面试官：听起来像背了结论。那为什么会解析两次？是谁在解析？

🙋‍♂️我：……应用先 resolve 一次做黑名单，HTTP 客户端发请求时又 resolve 一次。

👔面试官：对了一半。那如果我把校验写得很严，私网段全拦了，是不是就稳了？

🙋‍♂️我：应该……差不多？

👔面试官：不够。校验和连接不是同一次查找，中间就有窗口。再问一句：重定向、多条 A 记录、IPv6 映射地址，你打算怎么拦？

🙋‍♂️我：呃……

👔面试官：你一直在说「换 IP」，却没把检查时用的地址和真正连出去的地址钉死成同一个。从头捋：SSRF 防什么、DNS 重绑定打的是哪一步、怎么关窗口。

我卡住了。

![配图](/images/posts/2247484686/1.png)

面试现场：第一次答浅，被追问卡住

这道题考的不是你会不会背「TTL 很短」，而是你知不知道：DNS 重绑定不是又一种绕过姿势，而是校验与使用之间的 TOCTOU。下面按我现在会答的顺序重新讲。

────
💡 简要回答
────

SSRF 的本质是：服务端替攻击者去发起本不该由用户决定的出站请求。

常见目标是云元数据 169.254.169.254、内网管理口、本机回环上的管理接口。

常见的第一层防御是：拿到用户给的 URL → 解析主机名 → 看 IP 是不是私网/回环/链路本地 → 不是才放行。

这一层对「直连 IP」或「固定解析到内网」有效，但对 DNS 重绑定无效。

原因很简单：

1.校验阶段 DNS 答了一个安全的公网 IP，检查通过。

2.HTTP 客户端真正 connect 时会再解析一次。

3.攻击者控制权威 DNS，把 TTL 压到 0/1，第二次答出内网或链路本地地址。

所以正确总纲只有一句：解析、校验、连接必须用同一次结果；把通过校验的 IP pin 住，禁止客户端再查 DNS。

再补三条：

·重定向每一跳都重新走同一套校验。

·多条 A/AAAA 里任意一条危险就整拒。

·私网定义要覆盖链路本地、CGNAT、IPv4-mapped IPv6，不能只拦 10/8、127.0.0.0/8。

────
📝 详细解析
────

为什么「校验过了」还会打到内网？

![配图](/images/posts/2247484686/2.png)

校验与连接之间的 TOCTOU 窗口

把流程拆成四步就清楚了。

第一步：用户可控的 URL 进来。Webhook、头像拉取、文档预览、OIDC discovery、「帮我抓这个链接」一类功能，都算。

第二步：业务侧做 SSRF 检查。dns.lookup / getaddrinfo，看结果是不是危险网段。

第三步：检查通过，把原始 hostname 交给 HTTP 客户端。

第四步：客户端自己再 resolve，再 connect。

第 2 步和第 4 步之间，没有把「我刚刚认可的那个 IP」绑定到 socket 上。

攻击者只要在权威 DNS 上交替回答，就能让第 2 步看见公网、第 4 步连上内网。

这就是经典的 Time-of-Check to Time-of-Use。

业务上这很常见：很多团队以为「我们已经 resolve 过了、黑名单很全」，审计报告里也能勾上 SSRF 防护，但一测重绑定就穿。

2026 年仍有产品因为「先校验再交给默认 HTTP 客户端」被公开记成 DNS-rebinding SSRF。同一类洞，换个壳还会再来。

攻击怎么成立：讲识别条件，不背 payload

![配图](/images/posts/2247484686/3.png)

DNS 重绑定攻击链路

我会按识别条件讲，而不是背利用串。

条件一：出站目标由用户影响。

URL、host、回调地址、图片地址、导入源，只要服务端会替用户去拉，就在攻击面里。

条件二：存在「先查后连」的两段式代码。

典型味道是：自己写一段 isPrivate(ip)，通过后把字符串形式的 hostname丢给 requests / axios / HttpClient / curl。

客户端默认会再解析。

条件三：攻击者能控制该主机名的权威 DNS。

不一定要攻你的 DNS，他自己的域名就行；TTL 设得很短，甚至 0。

条件四：危险地址集合被漏拦，或只拦了「第一次答案」。

除了 RFC1918 和 loopback，还要盯：

·链路本地 / 云元数据：169.254.0.0/16（含 169.254.169.254）

·CGNAT：100.64.0.0/10

·本机其它形态：0.0.0.0/8、部分场景下的 ::1、ULA

·IPv4-mapped IPv6：::ffff:10.0.0.1 这种，只查 IPv6 字面量会漏

·多记录：一次应答里同时给公网 + 内网，客户端若碰巧连上内网那条就穿了——正确策略是任一危险则拒绝整主机名

条件五（常被忽略）：重定向。

第一次连的是安全 IP，302 到元数据地址或另一个可重绑定域名。

每一跳都要重新做「解析+校验+pin」，或者直接禁用跟随重定向。

满足一二三四，重绑定就成立；再加五，黑名单更容易被绕开。

面试里把这五条讲清，比甩一段伪代码更有说服力。

正确防御：怎么 pin 住检查过的 IP？

![配图](/images/posts/2247484686/4.png)

解析一次、校验、pin、再连接

防御的关键不是再加一层字符串黑名单，而是消灭二次解析。

做法 A：自定义 DnsResolver / 连接层校验。

在 HTTP 客户端真正用来查 DNS 的钩子里做校验：只返回已判定安全的地址，否则抛错。

Apache HttpClient 的 DnsResolver、部分语言的自定义 resolver，走的是这条路——检查者和连接者是同一个组件。

做法 B：先 resolve + 全量校验，再把结果 pin 进客户端。

例如 curl 的 CURLOPT\_RESOLVE（host:port:ip）、部分栈在 fetch/Client 上挂 pinned resolver。

注意：TLS 的 SNI 和 HTTP 的 Host 头仍应使用原始主机名，连接目标用 pin 住的 IP，避免证书校验和虚拟主机路由被带偏。

做法 C：根本缩小攻击面。

能用 IP 白名单或固定出站代理的业务，不要让用户任意指定 URL。

必须开放时，把所有「用户影响的出站」收敛到一个加固过的 HTTP 客户端，禁止业务代码各自 new Client()。

再叠几条工程细节：

·校验时用 lookup 的 all 模式，拿到全部 A/AAAA，任意一条危险就拒。

·私网判定做成统一函数，覆盖链路本地、CGNAT、mapped IPv6，单测要覆盖这些边界。

·默认不跟随重定向；若必须跟，每一跳完整重跑校验+pin。

·内网探测类功能（健康检查、端口探测）和应用出站通道隔离，避免「为了运维方便」开旁路。

业务场景怎么答才像做过事？

面试官常会接一句：「你们线上怎么防的？」我会按场景答，而不是背库名。

Webhook / 回调：租户配置的 URL 最危险。统一走 egress 网关，网关内 pin DNS，并按租户做配额和审计。

文档/图片预览：SSRF 收益高，响应常回显给用户。能关重定向就关；响应体做类型校验，别把内网错误页原样吐回。

云上环境：默认假设 Pod/主机能摸到元数据服务，SSRF 一旦成立就是凭据泄露。配合 IMDS 加固（如要求 hop limit / IMDSv2）和网络策略，是纵深，不是替代 pin。

一句话收束：DNS 重绑定考的不是你会不会挖洞，而是你知不知道「校验通过」不等于「连接安全」。

和相邻题怎么区分？

普通 SSRF：目标一开始就指向内网或元数据；防御重点是拦危险目标。

DNS 重绑定 SSRF：目标看起来是公网域名，危险发生在第二次解析；防御重点是 pin。

浏览器侧 DNS rebinding：经典是骗浏览器同源策略，和「服务端替你发请求」的 SSRF 不是同一条利用链，别混着答。

面试官若追问，可以说一句：「浏览器重绑定打的是同源；这里打的是服务端 egress 的 TOCTOU。」

排查时我会怎么动手？

拿到一段可疑出站代码，我不会先找 exploit，而是按清单对。

4.入口：哪些参数最终进了 URL / Host？是直接拼，还是只影响 path？

5.检查点：有没有私网判断？判断发生在解析前还是解析后？只看 hostname 字符串（如禁止 localhost）基本等于没防。

6.连接点：真正发请求的库是谁？它会不会自己 resolve？有没有把 IP 传进去，还是只传了 hostname？

7.重定向与协议：是否 allow\_redirects=True？是否允许 file://、gopher://、dict:// 这类异协议（语言和库差异很大，能关尽关）？

8.回显：响应是否返回给用户？内网错误页、元数据 JSON 一旦回显，危害从「盲 SSRF」升级到「信息带出」。

线上告警侧，可以盯：短时间内对同一外部域名多次解析结果跳变、出站目标落在链路本地/RFC1918、以及业务本不该访问的管理网段。

这些是防御验证和入侵痕迹，不是攻击教程。

面试里常见的错误答法？

我踩过的坑，正好可以反过来当加分项。

只答「TTL 很短」：TTL 是手段，不是本质；本质是两次解析没有绑定。

只补黑名单网段：网段永远补不全，且补全了也挡不住二次解析。

说「用 HTTPS 就安全」：TLS 不解决「连到了哪台机器」；SNI 仍是原主机名时，照样可能连到内网 IP。

把浏览器 DNS rebinding 和服务端 SSRF 混为一谈：被追问时立刻露馅。

答到位的标志是：面试官追问「校验很严呢？」你能立刻落到 pin / 同 resolver，而不是再报一个网段。

🎯 面试总结
────

![配图](/images/posts/2247484686/5.png)

答题框架四步

这道题的答题框架可以压成四步，顺序和上面一致。

1：先定本质。 SSRF = 服务端按用户意图出站。DNS 重绑定 = 校验与连接各解析一次形成的 TOCTOU，不是简单的「换个 IP 绕黑名单」。

2：讲清攻击成立条件。 用户可控 URL + 先查后连 + 攻击者控权威 DNS + 危险地址集合（含 169.254、mapped IPv6、多记录）+ 重定向未复检。

3：给唯一正确总纲。 同一次解析结果既用于校验也用于连接（自定义 resolver 或 CURLOPT\_RESOLVE 一类 pin）；多记录全拒策略；重定向每跳复检或禁用；出站客户端收敛成一个。

4：落到业务和排查。 Webhook/预览/OIDC 是高发面；排查时看代码是不是「自己 lookup 完还把 hostname 交给默认客户端」，看有没有 pin、有没有 follow redirect、私网函数覆盖是否完整。

把「TOCTOU → pin 同一地址 → 多记录与重定向」这条线讲顺，再补一句「校验通过不等于连接安全」，这题的深度基本就够了。
