👔面试官：SQL 注入怎么修？

🙋‍♂️我：用预编译，参数化查询，别拼接。

👔面试官：预编译和参数化是一回事吗？ORM 算不算？

🙋‍♂️我：差不多吧，都是把参数和语句分开……

👔面试官：那 ORDER BY 用户选列名、IN 一串 id、LIKE 模糊查，预编译还能直接挡住吗？

🙋‍♂️我：呃……ORDER BY 好像要白名单。

👔面试官：对。你刚才把「预编译」三个字当成万能补丁了。我想听的是：它到底防的是哪一层、什么位置根本绑不进占位符、哪些写法看起来用了 prepare 其实已经失效。

我卡住了。

![配图](/images/posts/2247484690/1.png)

白板开场：预编译不是万能补丁

这道题考的不是你会不会说「用预编译」，而是你能不能把 SQL 当成有结构的语言。对话只作钩子，下面按白板拆解：原理 → 正确用法 → 失效场景 → 怎么答。

────
💡 简要回答
────

数据库执行一条 SQL，本质上要先区分语句结构和数据值。

传统拼接是把用户输入嵌进整串 SQL，解析器重新看整串——输入里的引号、注释、分号都可能改结构。

参数化查询 / 预编译语句做的事是：先把带占位符的语句结构交给数据库（或驱动）编译/解析，再把用户输入作为类型化的数据绑上去。

此时输入再怎么长，也只是某个字面值，不会变成新的关键字或子句。

关键一句：预编译/参数化保证的是「值进值的位置」；它不保证「你把值塞进了标识符或关键字的位置」。

WHERE / SET / VALUES / LIMIT 用占位符；LIKE 要绑且转义；IN 要多占位符或数组接口；ORDER BY、表名、列名只走白名单映射。

────
📝 详细解析
────

预编译防的到底是哪一层？

![配图](/images/posts/2247484690/2.png)

拼接 vs 预编译：边界在哪

几个容易混的词，面试里建议一次说清。

预编译（Prepared Statement）：偏实现——语句先 prepare，再反复 execute。很多驱动会在服务端缓存执行计划，也有的是客户端模拟。

参数化（Parameter Binding）：偏接口——用 ? / $1 / :name 传值，而不是拼字符串。

防注入靠的是参数化语义，不是「调用了 prepare 这个 API 名字」。

ORM：多数安全路径底层仍是参数化；但 raw()、extra()、text().format()、字符串拼进 order\_by 会重新打开洞。

一句话收束：预编译不是免死金牌，它只保证「值是值」。

哪些位置可以绑，哪些根本绑不了？

![配图](/images/posts/2247484690/3.png)

可绑定 vs 不可绑定对照

能绑的，几乎都是数据字面量位置：

·WHERE id = ?、name = ?、created\_at > ?

·LIMIT ? / OFFSET ?（先转成整数再绑，别因为「看着像数字」就拼接）

·UPDATE ... SET col = ?

·INSERT ... VALUES (?, ?)

LIKE 的正确姿势是：整段模式当一个参数绑，同时对用户输入里的 %、\_、转义符做转义，并显式 ESCAPE。

只绑不转义，不一定是经典「改语句结构」的注入，但会造成超范围匹配或全表扫描型的滥用。

IN 列表：一个占位符只代表一个值。

正确做法是按元素个数生成 ?,?,?，或使用数据库支持的数组/ANY($1) 一类接口。

把逗号拼好的字符串塞进一个 ?，在语义上就错了——很多栈会当成单个奇怪字符串，少数错误封装则会退回拼接。

标识符位置（表名、列名、ASC/DESC）不能靠占位符解决——标准 SQL 里占位符不能代表标识符。

唯一稳妥的是白名单映射：用户输入只做 map 的 key，真正拼进 SQL 的是你写死的安全片段。

看起来 prepare 了，为什么还会失效？

![配图](/images/posts/2247484690/4.png)

五条失效路径示意图

面试官爱问「预编译失效的场景」，我按成因分成五类。每类只讲原理、怎么认、怎么修，不给可直接复制的攻击串。

1. 占位符根本绑不了的位置（最常见）

原理：ORDER BY 列名、排序方向、动态表名/列名、部分数据库的函数名，占位符语法不允许。开发者于是写成 "ORDER BY " + userInput。

怎么认：代码审查时搜 order、sort、tableName 拼进 SQL 的路径；动态报表、后台「任选字段排序」是重灾区。

怎么修：列名 → 枚举/字典映射到固定列；方向 → 布尔或二值映射到 ASC/DESC；表名 → 重新设计，避免用户选表。

过滤特殊字符、正则「只允许字母数字」不是等价方案，漏一个字符集或编码层就会破。

2. 半参数化：一部分绑了，一部分仍拼接

原理：WHERE id = ? 很规矩，但后面又拼了 AND " + clientFilter，或把整段用户提供的「额外 SQL 条件」贴上去。注入窗口在拼接那一段。

怎么认：同一条语句构造路径里，同时出现 placeholder 和字符串 +/format/f"...{user}..."。

怎么修：条件构造也走参数化 API 或 Query Builder；任何「用户自定义过滤」只能映射到预置条件模板。

3. 客户端模拟预编译 / 错误的转义封装

原理：部分驱动在旧协议或特定模式下会模拟 prepare：先在客户端把参数转义拼回 SQL，再当普通语句发送。

若转义与当前字符集、连接编码不一致，历史上出现过宽字节等方式让转义失效（经典讨论多在老旧 MySQL + 错误字符集组合）。

现代默认配置好很多，但不能在面试里把它说成「神话般永远不可能」。

怎么修：开启真正的原生预处理、统一 UTF-8、关闭 multiStatements；业务层仍坚持参数化 API，不手写转义。

4. ORM / 框架的「逃生口」

原理：框架安全默认值只覆盖常用 API。rawSQL、whereRaw、orderByRaw、Session.execute(text(f"..."))、字符串拼进 Criteria，都会绕过绑定。

怎么认：静态扫描或 Code Review 盯 Raw/text( / 字符串格式化进查询；看动态排序、动态字段投影有没有走白名单。

怎么修：禁止业务直接拼 raw；封装唯一的「动态排序」工具函数，内部只做白名单。

5. 二阶与「存储后再拼」

原理：入库时用了参数化，取出后在另一处拼进 SQL 或拼进拼接型命令。存储时安全，使用时不安全。

怎么认：追踪「用户可控字符串」的数据流，看第二次使用点是不是又当代码拼了。

怎么修：任何执行点都重新参数化；不要假设「库里的都是干净的」。

补充两个常被追问但不算「预编译失效」的点，避免答混：

·宽字节 / 编码问题：多发生在「手动转义 + 错误字符集」，不是参数化本身的锅；但若你的「预编译」其实是模拟拼串，就要一起答。

·存储过程：只有过程内部也用参数化/绑定才安全；过程里再拼接用户参数，洞只是换了个房间。

真实业务问题长什么样？

电商后台排序：前端传 sortBy=price，后端拼 ORDER BY price——表面正常；一旦接受任意字符串，就变成标识符注入。修法是 map：{"price":"price","sales":"sales\_count"}。

批量删除 / 导出：前端传一串 id，后端图省事 "IN (" + ids + ")"。修法是拆成数组，生成等长占位符。

搜索框 LIKE："%" + keyword + "%" 直接拼——既可能注入（若无参数化），也可能在有参数化时被 % 拖垮性能。修法是绑定 + 转义通配符。

多租户报表：按租户选不同分表，用用户输入当表名后缀——这是设计味很重的坑，优先改成租户 id 映射分表，而不是拼接表名。

和「转义防注入」怎么对比？

面试官有时会说：「那我全部 addslashes / mysql\_real\_escape\_string 不行吗？」

我的对比口径是：

·转义是在字符串层面猜「怎么把危险字符变无害」，强依赖字符集、引号风格、是否包在引号内；漏一种上下文就破。

·参数化是在协议/API 层面把数据和语句分开，不依赖你有没有猜对转义规则。

·标识符仍然两边都搞不定，必须白名单——这一点要主动说，避免被理解成「参数化万能」。

性能问题上也可以加半句：现代驱动里 prepare + execute 的开销通常可接受；即便某条语句只跑一次，为了安全也应参数化，别用性能当借口退回拼接。

审查时有哪些具体抓手？

比起背概念，面试官更爱听你怎么在代码里找洞。

1.全局搜拼接：+、format(、f"、sprintf、字符串模板进 SQL。

2.搜逃生 API：raw、whereRaw、orderByRaw、execute(text(、createNativeQuery。

3.动态排序/动态表：任何把请求参数直接拼进 ORDER BY / FROM 的路径，默认标红，直到看到白名单 map。

4.驱动配置：是否允许多语句、字符集、是否原生 prepare。

5.数据流二阶：留言、文件名、导出模板名——入库安全、出库又拼进 SQL 的点。

修的优先级也要说清：先改成参数化/白名单，再谈 WAF 与监控。WAF 对编码变形、二次注入并不总可靠，不能当主防。

若被问到「NoSQL 有没有预编译」：答「协议不同，但思想同类——别把用户 JSON 直接当查询结构；对操作符做白名单/类型约束」。点到为止，别跑题。

怎么组织 90 秒口述？

![配图](/images/posts/2247484690/5.png)

面试答题骨架

我会这样组织 90 秒口述：

1：先讲边界。 SQL 注入成功 = 用户输入参与了语句结构。参数化把输入钉在「值」的位置，结构在 prepare 时已定。

2：再讲正确用法。 WHERE/SET/VALUES/LIMIT 用占位符；LIKE 要绑且转义；IN 要多占位符或数组接口；标识符只走白名单映射。

3：主动说失效场景。 ORDER BY/表名/半参数化/ORM raw/二阶使用——证明你知道「调用了 prepare」不等于「整条链路安全」。

4：落到审查口诀。 搜拼接与 \*Raw；看动态排序；看字符集与多语句开关；看取出后再拼的点。

5：防御层次。 主防是参数化 + 标识符白名单；辅防是最小权限账号、关详细报错、WAF 仅作纵深。

────
🎯 面试总结
────

收一句：预编译不是免死金牌，它只保证「值是值」；失效几乎都出在「你把用户输入放进了值以外的位置」或「你以为绑定了其实在拼」。

会不会用预编译，考的是 API；知不知道它何时失效，考的是你有没有把 SQL 当成「有结构的语言」而不是字符串。

把边界、可绑位置、五类失效、审查抓手这条线讲顺，这题就立住了。
