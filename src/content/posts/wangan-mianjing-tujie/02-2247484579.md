面试官："容器安全聊一下，Docker 逃逸了解吗？怎么从容器里跑到宿主机上？"

我："最典型的两种：容器用 --privileged 起的，或者把宿主机的 docker.sock 挂进了容器，就能逃。"

面试官："那是运维直接给你开了后门。要是没特权，也没挂 socket 呢？"

我："那就看挂了哪些宿主机目录，比如挂了 / 或者 /etc，能直接改宿主机文件。"

面试官："也还是配置问题。capability 呢？容器默认会保留一批能力，你知道哪些危险吗？给了 CAP\_SYS\_ADMIN 你能干什么？"

我卡住了。

![配图](/images/posts/2247484579/1.png)

复盘才想明白：我背了一堆"逃逸姿势"，却没有一条主线。面试官真正想听的，是容器凭什么隔离、每种逃逸打的是哪一层、拿到一个容器你先查什么。下面按我现在会答的顺序重新捋。

---

简要回答

先把地基讲清楚：容器不是虚拟机，它和宿主机共享同一个内核。 一个进程"像是被关在容器里"，靠的是四样东西叠加：

·namespace：隔离视图(进程、网络、挂载、用户等)，让容器只看得见自己的世界；

·cgroup：限制资源用量；

·capabilities：把 root 的全权拆成几十个小权限，容器默认只保留一个很小的子集；

·seccomp + LSM(AppArmor/SELinux)：限制能调用哪些系统调用、能访问哪些资源。

所谓逃逸，就是想办法凿穿这四层里的某一层，拿到宿主机内核或宿主机 root 的执行能力。 顺着这条主线，我把逃逸分成三大类、六种常见路径：

一是配置给的：特权容器、挂载宿主机敏感目录、挂载 docker.sock。本质是运维把隔离层主动拆掉了。

二是权限给的：容器被额外授予了危险 capability，比如 CAP\_SYS\_ADMIN、CAP\_SYS\_MODULE、CAP\_DAC\_READ\_SEARCH、CAP\_SYS\_PTRACE。

三是实现/内核漏洞：runc、containerd 的漏洞(CVE-2019-5736、CVE-2024-21626)，以及宿主内核漏洞(Dirty Pipe、Dirty COW)。

中间还有两个"配置 + 权限"配合才成立的经典手法：cgroup 的 release\_agent 和 procfs 的 core\_pattern。

排查口诀我放在最后，一句话先记住：拿到一个容器，先看 capability、再看挂载、再看 seccomp/AppArmor、最后对内核和 runc 版本。

详细解析

先建模：容器靠什么隔离，逃逸打的是哪一层

![配图](/images/posts/2247484579/2.png)

把这张图记住，后面每一种逃逸都能对号入座：

·打穿 capabilities / seccomp 那层 —— 对应"权限给多了"，比如 CAP\_SYS\_ADMIN 让你能 mount、能玩 cgroup。

·绕过 namespace / 挂载隔离 —— 对应"配置给多了"，比如挂了宿主机目录、挂了 docker.sock，相当于容器直接伸手到宿主机文件系统或 Docker 守护进程。

·直接打 共享内核 —— 对应内核或 runc 漏洞，这层一破，前面几层都形同虚设。

一句话：容器的隔离是"纸糊的墙"还是"钢筋混凝土"，取决于配置。默认配置其实不弱，大多数真实逃逸都是因为有人把墙拆了。

逃逸方式分类

![配图](/images/posts/2247484579/3.png)

下面逐类讲，每种只讲三件事：原理(打的哪层)、触发条件(什么情况下成立)、怎么防/怎么查。 具体的攻击代码不展开，重点是能看懂、能排查。

一、特权容器(--privileged)

原理：--privileged 不是"多给一两个权限"，而是几乎把运行时保护全关了：授予所有 capability、解除设备 cgroup 限制、很多内核文件系统不再只读挂载、procfs 的 masked 路径消失、seccomp 停用、AppArmor/SELinux confinement 停用。这一层层保护一撤，容器里的 root 基本就等于宿主机的 root。

触发条件：容器以 --privileged 启动，且容器内是 root。此时常见的落地方式有两条：一是宿主机的块设备(整块磁盘)在容器里直接可见，挂载它就能读写宿主机根文件系统；二是后面要讲的 release\_agent、core\_pattern 这些手法在特权下几乎无门槛。

怎么查/怎么防：生产环境原则上禁用 `--privileged`；真需要某个能力就单独 --cap-add。排查时看 /proc/self/status 的 CapEff 是不是一长串全 1(0000003fffffffff 这种)，看设备节点是不是都能访问，看 /proc/sys 是不是可写。Kubernetes 里用 Pod Security / 准入控制挡掉 privileged: true。

二、挂载宿主机敏感目录 / docker.sock

原理：容器的文件隔离靠的是挂载命名空间。一旦把宿主机的敏感路径挂进容器，这层隔离就等于开了个洞：

·挂了 /、/etc、/root/.ssh、/var/spool/cron 这类目录，就能改宿主机的 passwd、写 authorized\_keys、下 cron —— 不用"逃"，直接改宿主机。

·挂了 `/var/run/docker.sock`，相当于把 Docker 守护进程的控制接口交给了容器。谁能跟这个 socket 说话，谁就能让守护进程新建一个挂载了宿主机 `/`、带特权的容器，从而拿到宿主机 root。这也是 CI runner、"DinD"场景最容易踩的坑。

·挂了宿主机 /proc、/sys，则把本该被 mask 的内核接口暴露了出来(接 core\_pattern 那一节)。

![配图](/images/posts/2247484579/4.png)

触发条件：对应的宿主机路径被 -v 挂进容器，且可写(docker.sock 只要可读写 socket 即可)。

怎么查/怎么防：cat /proc/mounts、mount 看有没有宿主机目录、有没有 docker.sock。原则是不要把 docker.sock 挂进容器，确有编排需求就走有鉴权的 API 或专门的代理；必须挂宿主目录时尽量只读(`:ro`)、最小范围；容器内不以 root 运行，开启 userns-remap，让容器 root 映射成宿主机的普通用户。

三、危险的 capabilities

原理：Linux 把 root 的全权拆成了几十个 capability。Docker 默认只保留一个较小的白名单，CAP\_SYS\_ADMIN、CAP\_SYS\_MODULE、CAP\_SYS\_PTRACE、CAP\_DAC\_READ\_SEARCH默认都不在里面。一旦有人 --cap-add 了它们，等于在隔离墙上单独开窗：

·CAP\_SYS\_ADMIN：权力最大的一个，能 mount、能操作 cgroup。它是下面 release\_agent 手法的前提。

·CAP\_SYS\_MODULE：能加载/卸载内核模块。容器里塞一个恶意内核模块，就直接进了 ring 0，可以无视一切隔离改内核 —— 等于逃逸的终极形态。

·CAP\_DAC\_READ\_SEARCH：能绕过文件读权限检查，还能用 open\_by\_handle\_at 按 inode 句柄打开文件。历史上的 "shocker" 就是靠它，在有宿主机 bind mount 的前提下，爆破 inode 句柄去读宿主机的 /etc/shadow。Docker 很早就默认丢掉了这个 cap，并用 seccomp 挡 open\_by\_handle\_at。

·CAP\_SYS\_PTRACE + 容器与宿主共享 PID namespace：能 ptrace 注入宿主机上的进程，借它的身份执行代码。

触发条件：容器被显式 --cap-add 了这些能力(或用了 --privileged 一次性全给)；部分手法还要求共享宿主 namespace 或存在 bind mount。

怎么查/怎么防：capsh --print 或读 /proc/self/status 的 CapEff/CapBnd，对照哪些是危险 cap。防御上先 `--cap-drop ALL` 再按需加回，坚决不加 SYS\_ADMIN/SYS\_MODULE/SYS\_PTRACE/DAC\_READ\_SEARCH；加 --security-opt no-new-privileges；别关 seccomp。

四、cgroup 的 release\_agent

原理：cgroup v1 有个"空组通知"机制。当一个 cgroup 开启了 notify\_on\_release，并且它里面最后一个进程退出时，内核会以宿主机 root 身份、在宿主机的命名空间里执行该 cgroup 层级根目录下 release\_agent 文件里写的那个程序。换句话说，谁能写 release\_agent，谁就能让内核替它在宿主机上跑一个指定程序。

触发条件(都满足才成立)：容器内是 root；有 CAP\_SYS\_ADMIN(才能 mount cgroupfs)；没有 AppArmor/seccomp 挡住 mount；cgroup 文件系统可读写。典型步骤是：挂一个 cgroup 控制器、建一个子 cgroup、打开 notify\_on\_release、把一个"宿主机和容器都能看到的脚本路径"(通常经由 overlay 的 upperdir 映射)写进 release\_agent，再让子 cgroup 里的进程退出来触发。--privileged 下这些前提天然满足。

这里有个要点能体现深度：CVE-2022-0492 曾经让这套手法在"新用户命名空间里"就能做，不需要在初始命名空间里真的有 CAP\_SYS\_ADMIN；内核已修复，现在写 release\_agent 要求在初始 user namespace 里具备 CAP\_SYS\_ADMIN。

怎么查/怎么防：别给 CAP\_SYS\_ADMIN，别让容器能 mount cgroupfs，保留默认 AppArmor/seccomp；升级内核修掉 CVE-2022-0492；运行时监控对 release\_agent、notify\_on\_release 的写入。

五、procfs 的 core\_pattern

原理：/proc/sys/kernel/core\_pattern 决定进程崩溃产生 core dump 时由谁来处理。如果它的值以管道符 | 开头，内核会把后面的路径当成处理程序，在进程崩溃时以宿主机 root、在初始命名空间里执行它。关键点是：这个设置是全机唯一、不受 namespace 隔离的，容器里改了就是改了宿主机的。

触发条件：/proc/sys 在容器里可写(特权容器会把它重新挂成可写；默认容器是只读，写会直接 EROFS)，并且处理程序路径在宿主机侧可达(常借 overlay 的 upperdir 这种"容器里写、宿主机能看到"的目录)。另一种情形是宿主机的 /proc 被直接 bind mount 进了容器。之后在容器里故意制造一次 core dump，内核就会在容器外把那个程序以 root 跑起来。

怎么查/怎么防：默认容器 /proc/sys 就该是只读的，别用 --privileged 把它改回可写，也别把宿主机 /proc 挂进容器；读 /proc/mounts 确认 /proc/sys 是 ro；运行时监控对 core\_pattern 的写。

六、runc / 内核漏洞

前面几类都是"配置或权限给多了"。这一类不一样：哪怕配置很规范，底层组件有洞照样能逃。

·CVE-2019-5736(runc)：容器内的 root 让 runc 去执行 /proc/self/exe，这个符号链接指向宿主机上的 runc 二进制。攻击者保留一个对它的文件描述符，等 runc 退出后把宿主机的 runc 覆盖成自己的程序；下次宿主机再调 runc(建容器、exec)，就以宿主机 root 跑了攻击者的代码。修复方式是 runc 启动时把自己复制进一块内存文件(memfd)并封存，/proc/self/exe 不再指向宿主机二进制。

·CVE-2024-21626(Leaky Vessels，runc ≤1.1.11)：runc 内部泄露了一个指向宿主机 /sys/fs/cgroup 的文件描述符。如果把容器的工作目录(WORKDIR / process.cwd)设成 /proc/self/fd/<那个号>，进程的工作目录就落到了宿主机文件系统里，从而能访问整个宿主机。一个恶意镜像就能触发。runc 1.1.12 修复。

·Dirty Pipe(CVE-2022-0847)：内核页缓存漏洞，能改写本该只读的文件。当 runc 以只读 bind mount 暴露宿主机二进制时，可借它改写宿主机 runc 达成逃逸。影响 5.8 ~ 5.16.11/5.15.25/5.10.102 之前的内核。

·Dirty COW(CVE-2016-5195)：更老的写时复制竞争条件漏洞，同样能用来改写只读文件、提权乃至逃逸。

触发条件：对应组件处于受影响版本。这类漏洞的"触发条件"基本等于"没打补丁"。

怎么查/怎么防：升级是唯一正解 —— 盯紧 runc、containerd、Docker 和宿主机内核的版本，对照 CVE 修复版本及时打补丁；只跑可信镜像(CVE-2024-21626 一个恶意镜像就能打)；配合只读 rootfs、no-new-privileges、userns-remap 做纵深防御。

怎么排查和防御：一张对照表

![配图](/images/posts/2247484579/5.png)

拿到一个容器，按这六步自查能不能逃：

1.身份：id 看是不是 root。

2.capability：读 /proc/self/status 的 CapEff，或 capsh --print，找 SYS\_ADMIN/SYS\_MODULE/SYS\_PTRACE/DAC\_READ\_SEARCH。

3.挂载：cat /proc/mounts，找 docker.sock、宿主机目录、可写的 cgroup、可写的 /proc/sys。

4.特权标志：CapEff 是不是全量，/.dockerenv 是否存在，设备节点是否随便可读。

5.seccomp/LSM：grep Seccomp /proc/self/status(0 表示没开)，看有没有 AppArmor profile。

6.版本：宿主内核、runc/containerd/docker 版本，对照 CVE。

防御清单(按收益从高到低)：

·不用 --privileged；--cap-drop ALL 再按需 --cap-add。

·不挂 docker.sock，宿主目录尽量只读、最小化。

·容器内不以 root 跑，开 userns-remap，加 --security-opt no-new-privileges。

·保留默认 seccomp 和 AppArmor/SELinux，别图省事 seccomp=unconfined。

·只读 rootfs，设资源上限。

·runc / containerd / docker / 内核及时升级，只跑可信镜像。

·上运行时检测：监控对 core\_pattern、release\_agent 的写，监控异常的 mount、call\_usermodehelper。

面试总结

这道题真正想考的，不是你能背几个"逃逸姿势"，而是你有没有一条主线：容器和宿主共享内核，靠 namespace / cgroup / capability / seccomp+LSM 四层隔离，逃逸就是凿穿其中一层。 照着这个框架答，层次就出来了：

1：先讲隔离模型。 容器不是虚拟机，共享内核；隔离靠四层。逃逸 = 打破某一层。

2：按来源分三类。 配置给的(特权、敏感挂载、docker.sock)、权限给的(危险 capability)、实现/内核漏洞(runc CVE-2019-5736、CVE-2024-21626、Dirty Pipe、Dirty COW)。中间两个经典手法 release\_agent 和 core\_pattern，都是"权限 + 配置"配合才成立。

3：每类讲清原理、触发条件、怎么防。 比如 CAP\_SYS\_ADMIN → 能 mount → 接 release\_agent → 内核以宿主 root 跑脚本；core\_pattern 是全机唯一、不受 namespace 隔离，所以特权容器改它等于改宿主机。

4：落到排查和防御。 拿到容器先看 cap、挂载、seccomp、版本这六步；防御核心就一句 —— 默认配置其实不弱，别自己把墙拆了：不特权、砍 cap、不挂 socket、不以 root 跑、及时升级。

把"隔离模型 → 分类 → 原理/条件/防御 → 排查清单"这条线讲顺，再点一句"大多数真实逃逸都是配置问题，不是内核 0day"，这题的深度基本就够了。
