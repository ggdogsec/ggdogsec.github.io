👔面试官：SSTI 了解吗？沙箱逃逸呢？

🙋‍♂️我：模板里能执行表达式，拼出 \_\_builtins\_\_ 再找到 os 就能命令执行。

👔面试官：听起来像背了利用链。现在引擎开了沙箱，把 \_\_class\_\_、\_\_globals\_\_ 一类属性拦了，你怎么论证「还危险」或「已经够安全」？

🙋‍♂️我：……换冷门属性绕？或者……认为沙箱够了？

👔面试官：两边都不完整。这题要的是威胁模型：模板求值边界在哪、沙箱拦的是语法还是对象图、逃逸证明看什么、防御优先砍什么。别先背链。

我卡住了。

![配图](/images/posts/2247484738/1.png)

面试现场：第一次背利用链，被追问卡住

这道题考的不是你会不会背某一条 Jinja/Twig 利用串，而是你知不知道：SSTI 的根因是「不可信输入进了模板编译/渲染」；沙箱是缓解，不是把不可信输入变可信。 下面按机制重讲。

────
💡 简要回答
────

SSTI（服务端模板注入）是：攻击者控制的数据被当成模板源码（或可执行表达式）去编译/渲染，于是读到服务端对象图，严重时可 RCE。

和「模板里输出变量被转义」的 XSS 不同：SSTI 发生在服务端引擎内部。

正确总纲：永远不要把用户输入拼进模板字符串；模板只接受数据上下文，不接受代码。

沙箱（Jinja SandboxedEnvironment、Twig 的沙箱扩展等）限制危险属性与函数，能提高利用成本。

但面试里要会说边界：沙箱是策略拦截，实现缺陷、允许的过滤器/函数、或业务把危险对象塞进 context，仍可能被打穿。

防御优先级：消除「用户输入 → 模板源码」> 固定模板 + 纯数据 > 沙箱与能力最小化 > 进程隔离与权限。

────
📝 详细解析
────

SSTI 和普通「模板渲染」差在哪一步？

![配图](/images/posts/2247484738/2.png)

不可信输入进入模板源码

正常用法：模板文件是开发者写死的；用户数据进 render(name=user\_name) 的 context。

危险用法：Template("Hello " + user\_input)，或把用户输入写进可被引擎加载的模板存储。

引擎会把字符串编译成 AST/字节码，再在上下文中求值。

一旦用户能注入表达式语法（因引擎而异），求值就变成「在服务器权限下跑一段模板语言」。

面试识别条件我只讲这些：

·存在服务端模板引擎（Jinja、Twig、Freemarker、Velocity、Thymeleaf 部分危险用法等）。

·有「用户可控字符串进入模板编译」的代码味：邮件模板后台、主题编辑器、报表标题拼接、错误页模板拼接。

·回显或盲注通道（时间、外带）能证明求值发生——证明用安全探测语义，不在面试里背 payload。

根因一句话：把数据当代码。

沙箱到底拦了什么？

![配图](/images/posts/2247484738/3.png)

沙箱拦的是属性/函数策略

以常见引擎为例讲模型（不绑定某条利用）：

沙箱会在属性访问、方法调用、过滤器执行前做策略判断。

例如禁止触及某些双下划线属性、禁止调用 os.system 一类、限制可用过滤器列表。

它做的是：缩小模板语言的能力面。

它不做的是：

·把「用户输入变成模板源码」这件事本身变成安全。

·保证业务 context 里没有高权限对象（数据库 session、密钥、请求对象）。

·保证所有过滤器/扩展都无副作用。

所以「开了沙箱」只能回答成：利用从「直接 RCE」变成「在策略漏洞或业务对象上找突破」；风险下降，根因还在。

「逃逸」在面试里应怎么论证？

![配图](/images/posts/2247484738/4.png)

从对象图走到危险能力

面试官说「沙箱逃逸」，想听的是推理，不是地下市场的链。

我会这样论证：

1.入口：不可信输入是否仍进编译器？若是，攻击面成立。

2.能力：沙箱策略列出的禁止项是什么？允许的函数/过滤器有无「读文件、造请求、拼内部 API」副作用？

3.对象图：context 里有没有应用对象？模板语言常能沿属性/下标游走；沙箱若只黑名单少量名字，可能被其它公开 API 绕到同类能力。

4.目标：逃逸的终点不一定是 os.system；读配置、打 SSRF、写文件、提权到管理功能，都算突破。

5.证明：在授权测试里用无害探测证明「表达式被执行」；再评估影响。面试只谈到方法论。

Twig 与 Jinja 细节不同，但地图一样：语法能力 × 沙箱策略 × context 对象 × 扩展函数。

若策略极严、context 极净、且用户不能改模板源码，则应明确说「这不是 SSTI，最多是模板侧 XSS/逻辑问题」。

防御优先序怎么排？

这是安全工程岗最爱听的部分。

P0：消灭 sink。 禁止用户输入进入模板编译；邮件/报表用固定模板 ID + 数据字段；CMS 的「自定义模板」当成代码发布，走审核与签名。

P1：引擎配置。 能关自动转义以外的「表达式执行能力」就关；禁用危险扩展；沙箱作为纵深，不是唯一控制。

P2：context 最小化。 只传渲染所需的标量/DTO；不传 request、config、orm session。

P3：运行环境。 渲染放到低权限 worker；无敏感文件系统与凭证；网络默认拒绝。

P4：检测。 代码审计搜「用户输入拼进 Template」；WAF 只能当噪声层，不能当结论。

一句话：防 SSTI 靠架构，不靠猜下一条逃逸链。

盲 SSTI 和「有回显」答题差别？

有回显时，可以用无害表达式证明「模板在求值」（例如算术或长度类探测），再停住——面试到此足够。

无回显时，论证换成：错误差异、时间差异、或受控的外带通道是否被策略允许。

重点仍是证明「不可信输入进入了引擎」，而不是展示破坏性命令。

安全工程面试里，主动说「授权测试只用无害探测、影响评估走隔离环境」，比甩一条破坏性链更加分。

若业务是「用户可编辑邮件 HTML 但不是模板引擎语法」，要先确认到底有没有引擎；很多「疑似 SSTI」其实是富文本 XSS，别贴错标签。

和相邻题怎么区分？

XSS：脚本在浏览器；SSTI 在服务端引擎。

CSTI（客户端模板注入）：浏览器侧模板引擎，影响不同。

反序列化：对象字节流唤醒；SSTI 是模板语言求值。别把「找 gadgets」话术直接套过来，但「对象图游走」可类比。

沙箱逃逸（通用）：浏览器/虚拟机/seccomp 等各有模型；这里特指模板沙箱策略被绕过或能力面过大。

代码审计时我会搜什么「味道」？

不靠猜引擎版本，先搜 sink 味道。

例如：字符串拼进模板构造函数；把请求参数写进模板目录；后台「自定义主题 / 邮件模板」直接存的是引擎语法而不是纯 HTML；渲染前 eval 式地选择模板名却未做白名单。

找到 sink 后，再看：沙箱有没有开、context 塞了什么、扩展函数列表、渲染进程权限。

这套顺序和答题框架一致：先证明风险面，再谈逃逸难度，最后给修复优先级。

常见错误答法？

一上来背利用串：面试官会打断，并怀疑你只会抄。

宣称「沙箱=安全」：忽略 sink 与 context。

只说「升级引擎」：版本有用，但根因是设计。

和 SSTI/XSS 混称：被追问执行位置就穿。

答到位的标志：能画清「输入→编译→沙箱策略→对象图→影响」，并给出 P0 消灭 sink。

────
🎯 面试总结
────

![配图](/images/posts/2247484738/5.png)

答题框架：sink、沙箱、对象图、优先级

这道题可以压成四步。

1：先定根因。 用户输入进入模板编译/渲染；数据被当成代码。

2：讲沙箱边界。 沙箱限制属性与函数，是缓解；不消除 sink，也不自动清洁 context。

3：论证逃逸看地图。 入口是否仍在、策略缝隙、context 危险对象、扩展副作用；终点不限于命令执行。

4：防御按优先级。 消灭拼接 > 固定模板与最小 context > 沙箱与关扩展 > 隔离与审计。

把「别背链，先讲 sink 与策略边界」稳住，这题就从脚本小子答法变成安全工程答法。
