👔面试官：Kubernetes 攻击面了解吗？

🙋‍♂️我：容器逃逸、未授权 API Server、etcd 未授权、ServiceAccount 权限过大……

👔面试官：名词挺多。你先画一张地图：从外到内，攻击者可能踩到哪些面？

🙋‍♂️我：外网进集群……然后 API Server……然后……节点？

👔面试官：顺序乱了，也缺块。kubelet、RBAC、Secrets、供应链、云上元数据，你准备搁哪儿？

🙋‍♂️我：……

👔面试官：别急着报 CVE。这题我要的是攻击面地图：每个面是什么入口、拿到什么、怎么守。逃逸只是其中一块。

我卡住了。

![配图](/images/posts/2247484682/1.png)

先给一张 K8s 攻击面地图

这道题考的不是单个 CVE，而是你有没有一张从外到内的地图。复盘后的答法：先丢地图，再按面分块讲入口与防守要点。

────
💡 简要回答
────

把集群想成多层：

1.控制面入口：API Server（6443）、etcd（2379/2380）、（少见的）不安全端口或匿名访问残留。

2.节点代理：kubelet（10250，历史只读 10255）、静态 Pod 清单目录。

3.身份与授权：RBAC、ServiceAccount Token、准入控制器。

4.数据面敏感物：Secrets/ConfigMap、挂进 Pod 的凭据、云厂商实例元数据。

5.工作负载与逃逸：特权/hostPath/hostNetwork、危险 capability，再到节点与横向。

6.供应链与准入：镜像、Helm/清单、CI 凭据、Admission Policy 是否真的在拦。

攻击者通常不是「一键打爆 K8s」，而是沿着地图找最软的一块：暴露的组件、过大的 RBAC、可逃逸的 Pod、能读到的 Secret、能进云的节点角色。

防守也按面做，而不是只修逃逸。

────
📝 详细解析
────

API Server 这扇正门怎么讲？

![配图](/images/posts/2247484682/2.png)

API Server 入口与绕过风险

入口：集群的唯一真相源。kubectl、控制器、准入 Webhook、用户与 ServiceAccount 的请求都汇这里。

暴露面包括公网误暴露、--anonymous-auth 未关、薄弱的认证、过宽的匿名/系统组绑定。

拿到意味着什么：认证授权一旦被绕过或凭据泄露，读写资源、拉 Secret、创特权 Pod、改 RBAC，都可能发生。

官方文档还单独强调一类「绕过 API Server 管控」的风险：有些能力让攻击者不再完整走「准入 + 审计」这条路（见下一节 kubelet / 静态 Pod / etcd）。

防守要点：

·控制面不要对公网裸奔；走 VPN/私网/受信跳板。

·关掉不必要的匿名访问；审计 system:anonymous / system:unauthenticated 绑定。

·开审计日志；强制 TLS；限制能绑定 cluster-admin 的人与 CI。

·用 Admission（Pod Security / OPA Gatekeeper / Kyverno 等）挡危险 Pod 规格——但要记住：直接打 kubelet/etcd 时，这些准入可能根本不在路径上。

为什么 etcd 直连是灾难级？

入口：etcd 存全部集群状态，含 Secret 对象。默认客户端口 2379。只有 API Server（以及你信任的备份工具）需要访问。

拿到意味着什么：能读 etcd ≈ 能读几乎所有 Secret 与 RBAC 对象；能写 etcd ≈ 能改权限、塞工作负载，且不走 Kubernetes 准入与 API 审计。

官方 hardening 口径非常硬：etcd 直连是集群级灾难。

防守要点：

·网络上把 2379/2380 锁死在控制面节点之间；工作节点、Pod 网络不可达。

·对等与客户端都用 mTLS；证书与密钥当最高机密轮换。

·开启 EncryptionConfiguration，让 Secret 落盘不是明文（至少不是裸 base64）。

·备份加密、权限最小化；警惕从备份或快照泄露。

kubelet 和静态 Pod 为什么是侧门？

![配图](/images/posts/2247484682/3.png)

kubelet / 静态 Pod 绕过路径

入口：每节点 kubelet API（常 10250）。若未正确配置认证鉴权，历史上出现过未授权 exec/attach/run 一类问题；只读端口 10255 在现代默认关闭，但旧集群仍可能见到。

另一条官方点名的旁路是：静态 Pod 清单目录/URL——kubelet 直接管，API Server 不审批。

另外，拥有某些 Node 子资源权限（如 nodes/proxy）的身份，可能把 API Server 当跳板去碰 kubelet，从而削弱「只靠 RBAC 看资源对象」的直觉。

拿到意味着什么：在节点上对 Pod 做 exec、拉日志、甚至影响同节点其它负载；静态 Pod 可被植入；这些动作不一定经过准入、也不一定出现在 API 审计里。

防守要点：

·kubelet 启用 webhook 或证书认证 + 鉴权；禁止匿名。

·网络隔离 10250，仅控制面/必要组件可达。

·收紧 RBAC：慎授 nodes/proxy、nodes/log 等子资源。

·保护静态 Pod 路径与节点本地文件权限；节点 OS 按主机加固。

RBAC 与 ServiceAccount 决定能走多远？

入口：被盗的用户 kubeconfig、CI 机器人、默认挂载的 SA Token、过宽的 RoleBinding/ClusterRoleBinding。

高危权限（讲原理级，不讲利用手册）：

·能 create/update pod 且可指定 SA、挂 hostPath、特权：常等于换身份或冲节点。

·能 get/list/watch secrets：直接读凭据；旧版 SA token 曾持久化在 Secret 里。

·能 escalate / bind 更高角色、或 impersonate：权限直升。

·能操作 validating/mutating webhook 配置、CSR、某些准入资源：改集群判决逻辑。

防守要点：

·默认 SA 不自动挂 token（automountServiceAccountToken: false），按需显式挂。

·角色按命名空间拆；禁止 \* 动词/资源的习惯性 ClusterRole。

·CI 用短时、受众绑定的令牌；人号开 MFA；定期扫「谁能读 Secret / 谁能创特权 Pod」。

Secrets 与云凭据怎么接到云账号？

入口：etcd 明文、被 mount 进 Pod 的文件/环境变量、镜像或清单里的硬编码、节点实例角色的元数据服务（169.254.169.254 一类）。

拿到意味着什么：数据库口令、云访问密钥、其它集群的 kubeconfig——横向从「一个 Pod」扩到「云账号/其它系统」。

OWASP K8s Top Ten 等材料把 Cluster-to-Cloud 横向单独成条，核心就是节点角色过大 + Pod 能碰 IMDS + 静态云密钥躺在 Secret 里。

防守要点：

·Secret 加密落盘；尽量外置到 KMS/Vault，Pod 短时取用。

·环境变量不如文件 mount 可控，但两者都能被读——根本是谁能进这个 Pod / 谁能 list Secret。

·NetworkPolicy 或 IMDS 加固，阻止普通 Pod 偷节点角色；节点 IAM 最小权限；优先 Pod 级身份（IRSA/Workload Identity 一类）替代「整节点一把钥匙」。

工作负载面：逃逸只是其中一块？

![配图](/images/posts/2247484682/4.png)

危险 Pod 规格与逃逸面

入口：privileged、hostPath/hostPID/hostNetwork、危险 capability、可写 Docker/containerd socket、过老的 runc/内核。

和单独考「Docker 逃逸」时同一套模型：共享内核，配置把墙拆了就会穿。

拿到意味着什么：节点 root、同节点其它 Pod 的挂载与 token、kubelet 凭据、进而碰控制面或云 API。

防守要点：

·强制 Pod Security 的 restricted/baseline；准入拒绝特权与敏感 hostPath。

·--cap-drop ALL 再按需加；只读根文件系统；非 root 运行。

·节点与运行时打补丁（runc/containerd/内核）；运行时检测异常 mount、特权启动。

供应链与准入卡在时间轴哪一段？

入口：投毒镜像、被篡改的基础镜像、泄露的镜像仓库凭据、CI 里的 kubectl 高权限、绕过签字与策略的部署路径（手动 apply、旁路流水线）。

拿到意味着什么：一次部署变成全集群副本执行恶意逻辑；比单漏洞更「宽」。

防守要点：

·镜像扫描 + 签名/provenance（Sigstore 等）+ 准入只放行受信仓库。

·构建与部署身份分离；生产 apply 权限极收紧。

·网络默认拒绝，再按需放行；监视异常出站。

怎么用一条路径把地图串起来？

用路径把地图串起来，面试官会觉得你见过体系，而不是卡片。

7.初始入口：暴露的工作负载漏洞、误公开的 API、被盗的 CI kubeconfig、投毒镜像。

8.身份落点：进到某个 Pod 后，先看挂没挂 SA Token、能 list 哪些资源、能不能读 Secret。

9.权限放大：过宽 RBAC → 读到更高特权 SA 或云密钥；或直接创建危险 Pod。

10.节点与云：逃逸或经 hostPath/特权进节点 → 碰 kubelet/容器运行时/实例元数据 → 出集群进云。

11.持久化：新建高权限绑定、静态 Pod、后门镜像、被改的准入 Webhook——这些要从控制面配置漂移去发现。

防守对应着拆：入口收拢（网络与供应链）、默认无 token、RBAC 定期扫、PSA 强制、etcd/kubelet 网络与认证、IMDS 与节点角色收敛、审计与运行时检测。

面与面之间有什么箭头？

答题加分的往往不是又多报一个组件名，而是说出依赖。

RBAC 决定 API Server 这扇正门里你能走多远；但 etcd/kubelet 旁路可以让你「不买票进门」。

Secret 面依赖存储与挂载：etcd 加密是底座，RBAC 少人能读是围栏，Pod 少挂载是房间锁。

逃逸面依赖工作负载策略：PSA/准入把危险规格挡在调度前；节点加固和补丁挡「规格看起来干净但运行时有洞」。

供应链是时间轴上的入口：镜像在构建时被污染，运行时地图上的其它面都会变成扩散通道。

云元数据是地图伸出去的一只手：集群内得手之后，风险是否变成云账号级，看节点角色与网络能否摸到 IMDS。

所以我画地图时会画箭头：外网/CI → 工作负载 → SA/RBAC → Secret/云；以及侧线 → kubelet/etcd。面试官一眼能看到你有结构。

答题时怎么控制深度？

·校招/一面：地图完整 + 每面一句入口一句防守就够。

·进阶追问：准备好解释「为什么 etcd/kubelet 是旁路」（不经准入/API 审计）、SA 与用户的区别、Secret 默认并非加密。

·别踩的坑：背一长串 CVE 编号却说不清面；把 Docker 逃逸整段背完却不提 RBAC；宣称「上了 Istio 就安全」。

按面防守的答题顺序

口述时我按固定顺序走，避免东一榔头：

12.先画地图（控制面 / kubelet / RBAC / Secrets与云 / 工作负载逃逸 / 供应链）。

13.每面三句话：入口是什么 → 失陷意味着什么 → 防守要点。

14.点明旁路：etcd、kubelet、静态 Pod 可能不走准入与 API 审计——这是深度信号。

15.收束：真实入侵多是「暴露 + 过宽权限 + 危险工作负载」组合，不是单靠一个 0day。

别只背逃逸和未授权：K8s 题考的是面，不是单个 CVE。

API Server 是正门，etcd/kubelet/静态 Pod 是侧门：侧门常绕过准入与审计。

RBAC 与 SA 决定攻击者进门后能走多远；Secrets 与云元数据把集群风险接到云账号。

工作负载面用 PSA/准入砍特权；供应链用签名与受信仓库收口。

把地图摊开讲完，最后用一句收束：K8s 安全不是单点漏洞竞赛，是控制面、节点代理、身份、机密、工作负载与供应链六块板——哪块最短，水就从哪漏。先画地图，再按面防守，这题就立住了。
