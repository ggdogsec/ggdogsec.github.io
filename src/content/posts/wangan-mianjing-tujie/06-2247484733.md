👔面试官：JWT 你们怎么验签的？

🙋‍♂️我：拆三段，拿 header 里的 alg，用对应密钥或公钥验 signature。

👔面试官：那攻击者把 alg 改成 none 呢？

🙋‍♂️我：……不验签直接过？我们会拒绝 none。

👔面试官：对了一半。再问：本来是 RS256 公钥验签，他把 alg 改成 HS256，把公钥当对称密钥用，你验不验得过？

🙋‍♂️我：呃……算法写在 token 里，库可能会顺着用。

👔面试官：关键来了：alg 是声明，不是策略。验签算法和密钥类型必须由服务端钉死，不能让 token 自己选。从头捋：结构、混淆、none、kid，以及你怎么答防御。

我卡住了。

![配图](/images/posts/2247484733/1.png)

面试现场：第一次答「看 alg」，被追问卡住

这道题考的不是你会不会背「JWT 三段」，而是你知不知道：谁有权决定用什么算法、用哪把钥匙。下面按我现在会答的顺序重新讲。

────
💡 简要回答
────

JWT 是 header.payload.signature 三段 Base64URL。

header 里常有 alg、typ，有时还有 kid。

payload 是声明（sub、exp、aud 等），本身不提供完整性。

验签的正确总纲只有一句：算法与密钥由服务端配置决定；token 里的 `alg` 最多做一致性校验，绝不能驱动选钥逻辑。

面试里我会先报三类高频坑：

1.alg=none：旧库或配置失误时跳过验签。

2.算法混淆：非对称（如 RS256）被改成对称（如 HS256），公钥被误当 HMAC 密钥。

3.`kid` 注入 / 选钥绕过：kid 进了文件路径或 SQL，或指向攻击者可控的密钥材料。

防御落点：白名单算法、固定验签函数、密钥按用途隔离、校验 exp/nbf/aud/iss，并警惕「库默认太宽松」。

────
📝 详细解析
────

为什么「看 header 里的 alg」是危险习惯？

![配图](/images/posts/2247484733/2.png)

alg 是声明不是策略

很多入门教程写成：读 alg → switch 到对应验签函数 → 用密钥验。

这在「诚实客户端」下能工作，但 JWT 的 header 和 payload 一样可被攻击者改写。

签名只保护「在某个算法+密钥下，这串字节没被改」。

它不保证「alg 字段对你是安全指令」。

如果验签代码把 alg 当成远程控制开关，攻击者就在改你的控制流，而不只是改业务字段。

所以安全答法是反过来的：

服务端先决定「这个接口只接受 RS256，用这把公钥」。

再解析 token，若 header 里 alg 不是 RS256，直接拒绝。

验签函数也固定为 RS256 验签，不再 switch(alg)。

none 算法到底打的是哪一层？

![配图](/images/posts/2247484733/3.png)

none 与跳过验签

none 的语义是：没有签名段，或签名为空。

规范里它存在，是为了「不需要完整性」的场景，不是给登录态用的。

出问题通常不是「有人发明了 none」，而是实现侧：

·旧版本库在 alg=none 时直接返回已解码 payload。

·自研验签写成 if alg == none: return true。

·网关与业务双重解析，其中一环没验签。

面试里我不背具体 CVE 号也能答清楚机制：

完整性检查被短路了。

防御极简：算法白名单不含 none；禁止空签名；验签失败与「无签名」走同一拒绝路径，不要「解码成功就算登录成功」。

算法混淆：RS256 改成 HS256 发生了什么？

![配图](/images/posts/2247484733/4.png)

算法混淆：公钥被当成 HMAC 密钥

这是比 none 更「像真题」的追问。

设定：服务端用 RS256，私钥签名，公钥验签。

攻击者把 header 的 alg 改成 HS256，并用你的公钥字节当作 HMAC 密钥去签一个伪造 payload。

若验签代码是：

「读 alg → 若是 HS256 就拿『密钥』做 HMAC」

而这里的「密钥」又错误地取成了「当前配置的公钥材料」，伪造 token 就会验过。

本质是两类错误叠在一起：

4.信任了 token 的 alg 选择（控制流被劫持）。

5.非对称验签与对称验签共用了密钥解析路径（密钥类型没钉死）。

正确模型：

·RS/ES/PS 族：只用私钥签、公钥验；验签 API 不接受「把公钥当 HMAC 密钥」。

·HS 族：只用独立的对称密钥；永远不要把公钥 PEM 放进 HMAC 密钥槽。

·一个 issuer / 一个 token 用途，对应一套固定算法，不在运行时混用。

补充一句边界：现代主流库大多默认收紧了，但自研网关、老 SDK、多语言混部时仍常见「一个服务严、一个服务松」。

kid、密钥轮换，和「选钥」攻击面？

kid（Key ID）本意是告诉验签方「用钥匙串里的哪一把」。

它是索引，不是「去哪儿读文件」的指令。

危险形态我只讲识别，不讲利用细节：

·kid 被拼进文件系统路径或 LDAP/SQL 查询。

·kid 指向 JWKS 里攻击者能植入的条目（JWKS URL 被 SSRF/劫持）。

·密钥轮换窗口里新旧密钥同时有效，但权限或算法约束不一致。

答法：kid 只允许在本地/信任 JWKS 的键集合里查找；查找失败即拒绝；JWKS 来源要 TLS+固定主机，并缓存与刷新策略可审计。

面试里怎么把验签答成一套清单？

我会按「验什么」而不是「调用哪个函数」说。

6.算法：服务端白名单；与 header 一致性校验；拒绝 none。

7.签名：用固定算法 API；密钥类型匹配；失败即拒绝。

8.声明：exp/nbf 时钟偏移；aud/iss 绑定到具体客户端与签发方；按需 jti 做注销/重放。

9.密钥：公私钥与 HMAC 密钥分槽；轮换可灰发；禁止把公钥当对称密钥。

10.传输与存储：HTTPS；HttpOnly Cookie 或安全的 token 存放；避免把长期 JWT 塞进可被 XSS 读的地方。

若面试官问「对称还是非对称」：内部微服务可用 HS；跨域、多签发方、需要分发验签能力时用 RS/ES，并配 JWKS。

一句话收束：JWT 的安全不在「用了 JWT」，而在「谁决定 alg 和 key」。

库与网关混部时，问题常出在哪？

单体里验签逻辑只有一份时，固定算法还好做。

一旦 API 网关验一次、业务服务再验一次，或旧服务用 HS、新服务用 RS，就容易出现「有的路径严、有的路径松」。

攻击者会找那条仍 switch(alg) 的老路径。

答法：统一验签中间件；密钥与算法配置中心化；上线前用「错误 alg / 空签名 / 公钥当密钥」三类负向用例做回归——测的是防御行为，不是教攻击步骤。

若用 JWKS 自动发现，要固定签发方主机名，并限制可接受的 kty/alg 组合，避免「JWKS 里突然冒出一把对称密钥」被当成合法验签材料。

和相邻题怎么区分？

JWT 伪造（无密钥）：通常要碰 none / 混淆 / 选钥错误；不是猜 payload。

JWT 泄露：XSS、日志、Referer；防的是机密性与存放，不是 alg。

Session vs JWT：无状态便利 vs 吊销困难；别把「无状态」说成「更安全」。

JWE：加密包装，和「只签名的 JWS/JWT」不是同一层；别混着吹「JWT 是加密的」。

负向用例怎么写才像做过工程？

面试官能听出来你是不是只背过概念。

我会说：上线前至少跑三类自动化负向用例——alg=none 必须 401/403；声明为 HS 但密钥槽只有公钥材料时必须失败；正确 RS256 但 aud 不匹配必须失败。

同时保留一类正向用例：合法 token、时钟偏移在 leeway 内、轮换期旧 kid 仍可验。

把这些写进 CI，比口头「我们用了官方库」更有说服力。

日志里只记 kid、iss、失败原因码，不记完整 token，避免二次泄露。

常见错误答法？

只答「用官方库」：官方库也要配置白名单；默认值会变。

只禁 none，不谈混淆：追问 HS/RS 时会露馅。

说「HTTPS 就够了」：HTTPS 防链路窃听，不防服务端验签逻辑被 token 劫持。

把 payload 当可信输入：即使验签过，仍要做业务授权；role=admin 不是验签能单独解决的。

答到位的标志：面试官说「alg 改成 HS256」，你能立刻落到 固定算法 + 密钥类型隔离，而不是再背一段 Base64。

🎯 面试总结
────

![配图](/images/posts/2247484733/5.png)

答题框架：声明、混淆、固定策略

这道题可以压成四步。

1：先定结构与信任边界。 JWT 三段；header/payload 可读可改；只有在正确算法与密钥下的签名才提供完整性。

2：点名两类经典坑。none 短路验签；RS↔HS 算法混淆把公钥误当 HMAC 密钥；扩展提 kid 选钥。

3：给唯一总纲。 算法与密钥由服务端策略钉死；alg 只做一致性检查；白名单、分槽、固定验签 API。

4：补声明与工程。exp/aud/iss；JWKS 与轮换；库配置审计；和 XSS/存放问题分开讲。

把「alg 是声明不是策略」讲顺，再跟上混淆与 none 的机制，这题的深度基本就够了。
