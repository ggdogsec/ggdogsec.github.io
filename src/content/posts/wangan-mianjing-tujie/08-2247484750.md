👔面试官：Windows 域里常问的 Pass-the-Hash，你怎么理解？

🙋‍♂️我：拿到账户的 NTLM 哈希，不用明文口令也能认证登录。

👔面试官：那哈希是「替代口令」还是「参与某协议计算」？和 Kerberos 有什么关系？

🙋‍♂️我：……好像是 NTLM 那边用的。域里默认不是 Kerberos 吗？

👔面试官：对，很多人卡在这儿。再追一层：Overpass-the-Hash 和 Pass-the-Ticket 分别传什么？TGT、TGS、PAC 各扮演什么角色？

🙋‍♂️我：哈希换票……票再传……PAC 是权限？边界有点糊。

👔面试官：这题考的不是背工具名，而是你能不能画一张图：凭据材料 → 协议路径 → 证明形态（Hash 还是 Ticket）→ 利用条件与防守排查。

我卡住了。

![配图](/images/posts/2247484750/1.png)

面试现场：答「拿到哈希就能登」，被追问 Kerberos 边界卡住

这道题考的是 Windows 认证里两套常见证明：NTLM 挑战应答里的哈希，和 Kerberos 票据体系里的 TGT / Service Ticket。下面按「材料—协议—边界—防守」重新答。

────
💡 简要回答
────

Pass-the-Hash（PTH）的本质：不还原明文口令，直接把 `NTLM Hash` 当作认证材料，参与 NTLM 挑战应答，从而以该账户身份访问资源。

它解决的是「我已经有哈希了，怎么完成一次被接受的认证」，不是「我怎么算出口令」。

域环境里还有第二套主流路径：Kerberos。客户端先向 KDC 的 AS 拿 TGT，再向 TGS 换目标服务的 Service Ticket，最后拿票访问服务。PAC（Privilege Attribute Certificate）通常嵌在票里，携带 SID、组成员等授权信息。

三条容易混的词要先钉死：

1.Pass-the-Hash：传递/使用的是哈希，协议面多落在 NTLM。

2.Overpass-the-Hash：仍以哈希为起点，但目标是向 AS 完成认证并拿到合法 `TGT`，进入票据体系。

3.Pass-the-Ticket：传递/复用的是已有票据（TGT 或 Service Ticket），协议面是 Kerberos。

面试总纲一句话：Hash 是燃料，Ticket 是通行证，协议决定怎么烧。

────
📝 详细解析
────

为什么「拿到哈希就能登」只答对了一半？

这句话缺了两样东西：协议和证明形态。

哈希本身不是「万能登录口令」。它是一串密钥材料：在 NTLM 里，它参与挑战应答的计算；在通向 Kerberos 的路径里，它可能被用来完成对 AS 的认证，从而换票。

所以浅答「有哈希=能登」会被立刻追问：登的是哪条协议？目标是 SMB 会话、LDAP 绑定，还是先换 TGT？

更稳的开场是：

PTH 描述的是一种凭据重用：用哈希代替明文口令完成认证；具体能不能成，取决于目标是否接受该协议与该账户的哈希材料。

Kerberos 正常流程里，TGT / TGS / PAC 各干什么？

![配图](/images/posts/2247484750/2.png)

Kerberos 正常认证简化流程

把 KDC 拆成两个逻辑角色（实现上常在同一台域控）：

·AS（Authentication Service）：验证「你是谁」，发 TGT。

·TGS（Ticket Granting Service）：验证「你有有效 TGT」，再为目标 SPN 发 Service Ticket。

五步记忆法（面试够用）：

4.客户端发 AS-REQ（用户身份相关信息）。

5.AS 回 AS-REP：得到 TGT + 会话密钥。TGT 的含义是「域已经认证过我」。

6.客户端带 TGT 与 Authenticator 发 TGS-REQ，声明目标服务 SPN。

7.TGS 回 TGS-REP：得到 Service Ticket（常口语叫 TGS 票）。

8.客户端对服务发 AP-REQ：Service Ticket + Authenticator，服务用自己的密钥解开票并核对。

PAC 要单独说清：它不是「另一张票」，而是票内常见的授权数据包——组成员、特权相关 SID 等。服务或域控后续做访问决策时，会用到这些信息。面试里把它放在「认证之后的授权材料」这一层，别和 TGT/TGS 三个名词挤成一团。

Authenticator 的角色是防重放、证明「此刻持票者掌握会话密钥」——你答到「票 + 时效证明」即可，不必背字段表。

拿到哈希之后，到底怎么「用」？PTH 与 Overpass 差在哪？

![配图](/images/posts/2247484750/3.png)

PTH 与 Overpass-the-Hash 概念对照

同一份 NTLM Hash，面试里至少要能画出两条概念路径：

路径 A：Pass-the-Hash（偏 NTLM）

·材料：哈希。

·动作：在 NTLM 挑战应答中直接使用该哈希参与计算。

·结果：目标若走 NTLM 且接受该账户，则建立以该身份的会话。

·特点：不必先经过「换 TGT」；证明形态始终是「哈希参与的应答」，不是「出示 Kerberos 票」。

路径 B：Overpass-the-Hash（哈希 → Kerberos）

·材料：仍是哈希。

·动作：用哈希完成对 AS 的认证，换取合法 `TGT`。

·结果：之后的访问可以完全走 Kerberos：再换 Service Ticket，必要时再谈票的移动与复用。

·特点：哈希是入场券的燃料，真正在后续跳转里亮出来的，往往变成了票。

边界口诀：

·问「PTH」：对方在听 NTLM + Hash。

·问「Overpass」：对方在听 Hash 换 TGT。

·二者起点相似，协议出口不同。

这里刻意不写任何可复制的工具参数或报文构造——面经要的是机制地图，不是操作手册。

Pass-the-Ticket 和 PTH 的边界怎么划，才不会混？

![配图](/images/posts/2247484750/4.png)

Hash 路与 Ticket 路边界

用「传递物」一刀切开：

| 名称 | 传递/复用的是 | 协议面 | 证明已成立的形态 |

|------|----------------|--------|------------------|

| Pass-the-Hash | NTLM Hash | 多为 NTLM | 挑战应答被接受 |

| Overpass-the-Hash | Hash → 换票 | 进入 Kerberos | 获得合法 TGT |

| Pass-the-Ticket | TGT / Service Ticket | Kerberos | 票在有效期内可被服务/KDC 接受 |

Pass-the-Ticket 的关键不再是「会不会算 NTLM 应答」，而是：

·票是否仍在生命周期内、是否被注销/密钥轮换废掉。

·票内 PAC 等授权信息是否与当前域状态一致（防守侧会关心校验与更新策略）。

·持票者是否处在能「出示」这张票的会话与主机上下文中。

一条常见叙事链（概念层）：

哈希材料 →（可选）Overpass 换 `TGT` → Pass-the-Ticket 在多台机器间复用票。

也可以不经过 Overpass，直接在 NTLM 面上做 PTH。面试时主动说「两条岔路」，比只背一个缩写更像理解过。

利用条件你怎么答？不谈步骤，谈前置。

面试官要的是「什么情况下这条路才走得通」，而不是操作清单。

我会从四类前置答：

9.材料可达：某处已出现可被重用的哈希或可被导出的票（内存、存储、备份、弱隔离的管理会话等）。这是「先失陷/先泄露」，PTH 本身不解释「哈希从哪来」。

10.协议可达：目标服务或中间跳板仍接受相应认证路径（NTLM 或 Kerberos）。若环境强制签名、限制 NTLM、或服务只认特定票据策略，材料有了也不一定打得通。

11.账户有效：账户未禁用、口令/密钥未轮换到使旧哈希失效、票未过期。轮换密钥会让旧哈希和旧票一起贬值。

12.横向面：高权限账户哈希/票的危害面更大（域管、服务账户、同一本地管理员口令复用等）。答危害时落到「身份等价」，不要只说「能登录」。

再补一句边界：PTH 讨论的是认证材料重用，和「破解口令」「黄金票伪造」不是同一层题。黄金票/银票涉及伪造与密钥材料（如 KRBTGT / 服务密钥），应单独开题，避免把「有哈希」和「能伪造任意票」混成一句。

防御与排查，面试里怎么答才像蓝队？

防守我不背产品名，按控制目标说：

减少哈希与票的暴露面

·最小权限与分层管理：日常办公与高权限账户隔离；避免在普通工作站上堆积域管会话。

·Credential Guard / 远程凭据防护一类能力：降低内存中凭据被轻易重用的概率（答到「保护的是派生凭据与哈希暴露」即可）。

·禁止或严格限制 NTLM；能 Kerberos 的路径优先 Kerberos，并配合签名与信道绑定等加固（具体开关名按你们环境说）。

·本地管理员口令随机化（如 LAPS 思路）：打断「一台中招 → 同口令哈希打遍网」。

·服务账户与 gMSA：减少长期静态口令/哈希。

让旧材料尽快失效

·高价值账户定期轮换；怀疑泄露时优先轮换，并评估 KRBTGT 轮换的影响面（这是变更，不是日常开关）。

·票生命周期与续订策略合理；异常长寿票要可解释。

检测与排查落点

·同一账户短时间从多主机发起认证、异常的 NTLM 使用比例、非常用地登录。

·Kerberos 侧：异常的 TGT/TGS 请求模式、服务票据与账户行为不匹配。

·终端侧：异常的高权限进程、可疑的凭据访问行为（讲「遥测类别」，不讲绕过）。

排查叙事可以是：先定「丢的是哈希还是票」→ 再定「协议是 NTLM 还是 Kerberos」→ 再追「哪台机器、哪个账户、时间窗」→ 最后做轮换与会话清理。

和相邻题怎么区分，避免答串题？

密码喷洒 / 爆破：猜的是口令；PTH 假设哈希已在手。

LLMNR/NBT-NS 投毒等中继类：核心是「把认证导到攻击者可控处」；可能与 NTLM 相关，但题眼是中继与签名策略，不是「哈希重用」本身。

Kerberoasting：要的是可离线尝试的服务票材料，题眼是弱服务口令与 SPN，不是 PTH。

黄金票 / 银票：伪造票据，依赖不同级别的密钥材料；和「重用真实哈希/真实票」要分开讲。

Pass-the-Cookie（Web）：浏览器会话令牌，不是 Windows NTLM/Kerberos 这套。

答串题的标志是：面试官问 PTH，你开始讲造票；问 PtT，你还在讲 NTLM 挑战。把「材料」和「协议」两轴拉开就不会乱。

常见错误答法？

「PTH 就是破解哈希」：方向反了；PTH 恰恰常假设不破解。

「域里只有 Kerberos，所以没有 PTH」：域偏好 Kerberos，但不等于 NTLM 路径消失；降级、兼容、特定服务仍可能走 NTLM。

把 Overpass、PTH、PtT 当成同义词：三者传递物与协议出口不同，是送分的边界题。

只答工具名：面试官要的是机制；工具会变，协议角色相对稳定。

防守只说「改密码」：要补协议限制、会话隔离、检测与票/哈希生命周期。

答到位的标志：对方说「那和 TGT 呢？」，你能立刻落到 Overpass 换票 vs PtT 传票，而不是再说一遍「有哈希就能登」。

────
🎯 面试总结
────

![配图](/images/posts/2247484750/5.png)

答题框架：材料、协议、边界、防守

这道题可以压成四步。

1：先定凭据材料。 明文口令、NTLM Hash、TGT、Service Ticket、票内 PAC——各是哪一层的东西。

2：再定协议路径。 PTH 多落在 NTLM 挑战应答；Kerberos 走 AS→TGS→AP；Overpass 是「哈希换 TGT」的桥。

3：用传递物划边界。 Hash 路是 PTH；Ticket 路是 PtT；中间的 Overpass 负责把燃料变成通行证。

4：收束到条件与防守。 材料从哪来、协议是否仍接受、轮换是否失效；防守讲暴露面、失效、检测排查三条线。

把口诀讲顺——Hash 是燃料，Ticket 是通行证，协议决定怎么烧——再跟上 TGT/TGS/PAC 的角色，这题的深度基本就够了。
